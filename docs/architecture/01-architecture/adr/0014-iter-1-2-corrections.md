# ADR‑0014: Iteration 1+2 corrections from adversarial review

## Status
Accepted — 2026-05-10. Amends ADRs 0003, 0004, 0005, 0006, 0010, 0011, 0013 with narrow corrections identified in the iteration‑4‑readiness adversarial review. Amended by [ADR-0019](0019-admin-ui-bff-and-write-auth.md): the AdminUiSignedRequest pattern from §14.5–14.6 is concretized — AdminJS sends BOTH a session cookie AND an Ed25519 JWT on writes; admin-api enforces cookie ↔ JWT agreement and resolves identity from the session.

> **AMENDED by ADR-0020 (2026-05-15):** §14.2 — Keycloak is now the sole IdP for operator-facing UIs, not just the default OIDC provider. The "pluggable via env var" posture remains in code but Keycloak is the only supported deployment. Internal auth is gated by `operators.internal_password_hash IS NULL` per D2-b. See [ADR-0020](0020-sso-keycloak-canonical-idp.md).

## Context
The adversarial review surfaced 13 issues across implementability, maintainability, security, and architectural alignment. Four were rated 🔴 critical (would break implementation) and five 🟡 high (significant debt). This ADR captures the agreed corrections in a single bundle before iteration‑4 contract drafting concludes. Each section amends one prior ADR. The amended ADRs remain immutable; their `Related` sections cross‑link to this ADR.

A sister ADR, [ADR‑0015](0015-liquibase-schema-source-of-truth.md), captures the related decision that **Liquibase is the source of truth for the schema**.

## Decisions

### 14.1 Change channel: global channels with application‑layer tenant filter (amends [ADR‑0010](0010-change-channel-postgres-listen-notify.md))

**Original**: tenant‑scoped channel names like `mintkey:t_acme:credential` per tenant.

**Problem**: a single proxy plugin process serving N tenants must `LISTEN` on `3 × N` channels, each holding a Postgres connection. At 100 tenants per instance this exceeds `max_connections` budgets and creates connection pressure unrelated to actual workload.

**Correction**: channels are **global, not per‑tenant**:
- `mintkey:service` — service.* events
- `mintkey:credential` — credential.* events
- `mintkey:agent` — agent.* and token.* events
- `mintkey:heartbeat` — liveness pings every 30 s

Each event payload still carries `tenant_id`. Subscribers receive all events on a channel and **filter at the application layer** by the tenants they care about. The `mintkey/internal/changes` (Go) and `mintkey.changes` (Python) wrapper packages enforce the filter as a single point of correctness.

**Consequences**:
- One LISTEN per channel per process (3–4 connections total) regardless of tenant count.
- Subscribers must explicitly configure their tenant set: per‑tenant subscribers pass a tenant list; global subscribers (Kong‑syncer, PlatformAdmin tooling) pass an explicit `[ALL_TENANTS]` sentinel. The wrapper **panics on startup** if no tenant scope is configured.
- An architecture test asserts every subscriber configures a tenant scope; an integration test fuzzes with cross‑tenant events to assert filtering correctness.

### 14.2 Service identity boot secret for the Vault Adapter client (amends [ADR‑0003](0003-credential-storage-strategy.md))

**Original**: ADR‑0003 said the OIDC client secret is stored in the Vault Adapter (dogfooding).

**Problem**: the Vault Adapter requires the caller to authenticate. The credential to authenticate the FastAPI to the Vault Adapter cannot itself live in the Vault Adapter — circular.

**Correction**: introduce a per‑service **boot secret** for Vault Adapter authentication:
- Each service that calls the Vault Adapter (Admin REST API, MCP Server, Credential Broker, Egress Proxy plugin) has a unique service identity (e.g., `svcid_admin_api`, `svcid_mcp`, `svcid_broker`, `svcid_proxy`).
- Each service's boot secret is a 32‑byte random token, provisioned at deployment time:
  - **Compose default**: generated by the seed job, written to a host file (mode 0400) and mounted into each service container at `/run/secrets/mintkey_service_token`.
  - **Production**: provided by the deployer via Kubernetes Secret, AWS Secrets Manager, etc.
- The Vault Adapter validates each call's boot secret in constant time against a hash stored in its file backend (a special "service identity" credential type alongside other credentials).
- Each service identity has a tenant‑aware **access policy** — e.g., `svcid_mcp` can read service metadata across its tenants but cannot read signing keys; `svcid_broker` can read signing keys for any tenant; `svcid_admin_api` has the broadest read+write.
- Rotation: re‑run the seed job (or its rotation subcommand). Old + new tokens both accepted during a configurable overlap window.

**Consequences**:
- Bootstrap is acyclic: seed job → service identities → each service starts with its boot secret → connects to Vault Adapter → fetches long‑lived credentials (OIDC client secret, broker signing keys, …).
- Compromise of one service identity is bounded by its access policy; not "any service can read anything".

### 14.3 OpenAPI: checked‑in YAML is canonical (amends [ADR‑0005](0005-admin-tech-stack.md))

**Original**: ADR‑0005 said FastAPI emits OpenAPI from typed handlers; iteration 4 also calls for `docs/contracts/rest/openapi.yaml`. Source of truth was ambiguous.

**Correction**: **the checked‑in `docs/contracts/rest/openapi.yaml` is canonical**. The FastAPI app's runtime OpenAPI must match it exactly. CI runs:

```sh
python -m admin_api.main --emit-openapi > /tmp/runtime.yaml
diff <(yq -y . docs/contracts/rest/openapi.yaml) <(yq -y . /tmp/runtime.yaml)
```

…and fails on any difference (after canonical sort by `yq`).

**Workflow for an API change**:
1. Edit the canonical YAML.
2. Update FastAPI handlers and Pydantic schemas to match.
3. CI verifies they agree.
4. Generated/Kiro‑driven server stubs read the YAML.

This makes the YAML the **spec input for Kiro**. The developer's job is to plug in business logic; types and routes are generated from the contract.

### 14.4 No plaintext credential cache in the Egress Proxy plugin (amends [ADR‑0004](0004-egress-proxy-kong.md), [ADR‑0011](0011-shared-go-stack.md))

**Original**: ADR‑0004 plugin caches plaintext credentials keyed by `(tenant_id, service_id, key_version)` with TTL ≤ JWT TTL.

**Problem**: 5 minutes of plaintext credential lifetime in the data‑plane node is the security window. Go's GC plus go‑pdk gRPC marshaling create copies the application can't reliably zero. The latency saving is small.

**Correction**: **drop the plaintext cache in the proxy plugin**. Every proxy hit calls the Vault Adapter via gRPC for the credential, uses it within request scope, and best‑effort zeros the byte slice before request completion. The Vault Adapter caches the **encrypted DEK** keyed by `(tenant_id, service_id, key_version)` so its work is one AES‑GCM decrypt per call.

**Latency math**:
- Round‑trip Vault Adapter ↔ Proxy plugin over UDS or local TCP: ~2 ms p50.
- AES‑GCM decrypt of < 1 KB ciphertext on cached DEK: < 0.1 ms.
- Net added latency: ~2–3 ms p50, well within the 10 ms p50 [S‑PERF‑1](../03-quality-attributes.md) budget.

**Security gain**:
- Plaintext lifetime in the data‑plane is per‑request (microseconds), not per‑cache‑TTL (minutes).
- A coredump of the proxy plugin process reveals at most one in‑flight credential, not a cache.

The Vault Adapter is sized to handle the load; horizontal scaling for production is a Phase 2 follow‑up.

### 14.5 All AdminJS writes go through FastAPI (amends [ADR‑0013](0013-adminjs-pin.md))

**Original**: ADR‑0013 split writes between AdminJS direct DB (non‑sensitive) and FastAPI dispatch (sensitive). Mitigation for non‑sensitive writes was DB triggers.

**Problem**: "non‑sensitive" is not a real category; DB triggers are operationally complex and easy to miss on new tables.

**Correction**: **all AdminJS writes route through FastAPI**:
- Read operations (list, show): direct DB via `@adminjs/sql` with tenant scoping in `before` hooks.
- Write operations (create, update, delete, custom actions): always POST to FastAPI.

The FastAPI is the **single audit chokepoint** for all state changes. AdminJS is a thin read‑mostly UI plus a write‑forwarder. DB triggers are dropped from ADR‑0013.

Iteration 4 contracts add the necessary FastAPI endpoints for every AdminJS‑triggered write.

### 14.6 AdminJS↔FastAPI: signed request with operator context (amends [ADR‑0013](0013-adminjs-pin.md))

**Original**: shared service‑to‑service token between AdminJS and FastAPI.

**Problem**: single static long‑lived secret; if leaked, an attacker can impersonate AdminJS to bypass operator authentication on writes.

**Correction**: AdminJS signs each FastAPI request with an asymmetric keypair:
- AdminJS holds the **private key** (mounted at deployment as a file or supplied by the deployer's secrets manager).
- FastAPI fetches AdminJS's **public key** from the Vault Adapter on startup (credential type `admin_ui_signing_key`); refreshes on a configurable cadence (default hourly).
- Each request from AdminJS to FastAPI carries a JWT (Ed25519, same algorithm as the broker uses) with claims: `iss="mintkey/admin-ui"`, `sub=<operator_id>`, `tnt=<tenant_id>`, `aud="mintkey/admin-api"`, `iat`, `exp` (60‑second TTL), `jti` (replay protection).
- FastAPI validates signature, exp, jti (denylist of recently‑seen jti for 5 min), and that the operator is authenticated and authorized for the action.
- Key rotation: same overlap pattern as ADR‑0006.

This eliminates the long‑lived static secret and binds every cross‑service call to a specific operator + tenant.

### 14.7 Audit hash chain is mandatory (formalizes a threat‑model recommendation)

**Original**: threat model said "append‑only + (optional) hash chain". Optional means not built.

**Correction**: hash chain is **mandatory from Phase 1**.
- Each audit row stores `prev_hash` and `hash`.
- `hash = sha256(canonical_json(event_minus_hash) || prev_hash)`.
- The first row in each tenant's audit log has `prev_hash = sha256("mintkey-audit-genesis-v1:" || tenant_id)`.
- The chain is **per tenant** (no cross‑tenant hash dependency, so tenant deletion or import doesn't break chains in other tenants).
- A scheduled job (default daily) walks each tenant's chain, recomputes hashes, and emits a `audit.chain.verified` event on success or `audit.chain.tampered` on discrepancy. Tampered chains alarm the operator immediately.

**Performance impact**: each audit insert reads the previous row's hash (per tenant) to compute the new one. This serializes audit emission **per‑tenant**, not globally. At 100 events/sec sustained per tenant, 10 ms/insert is plenty of headroom. At higher per‑tenant volume, consider per‑category chains within a tenant (defer to scaling‑specific ADR if it ever becomes hot).

### 14.8 RLS policy hygiene: architecture test (formalizes [ADR‑0008](0008-multi-tenancy-row-level-with-db-tier.md))

**Correction**: a CI step that, after Liquibase migrations run against a fresh test DB, asserts:
1. `pg_policies` has at least one row per table in the `public` schema except for explicit allowlist tables (e.g., the audit‑chain genesis table itself, schema migration tables).
2. No policy has `qual = 'true'` (a no‑op policy).
3. Every domain table has a `tenant_isolation` policy whose `qual` references `current_setting('app.current_tenant')`.
4. The `mintkey_app` role is the application role; `mintkey_migrate` is the migration role; the test verifies they exist with appropriate grants.

Failure of any check fails the build. The test lives at `tests/architecture/test_rls_coverage.sql` (PgTAP) or its Python equivalent.

### 14.9 JWT TTL ergonomics: agent SDK refresh‑before‑call pattern (note on [ADR‑0006](0006-token-format-and-binding.md))

**Original**: 10‑minute default TTL with no agent guidance.

**Correction**: the agent SDK (Python via the `mcp` SDK; future Go/TS) follows the **refresh‑before‑call** pattern:
- Before any operation expected to take >50% of remaining TTL, the SDK requests a fresh token.
- After receiving a 401 from the proxy due to expired JWT, the SDK requests a fresh token and retries once for **idempotent calls only**. Non‑idempotent calls surface the 401 to the agent caller.

This is documented in iteration‑4 MCP tool descriptions and in the agent SDK READMEs. For Phase 3+ (long‑running streams, MCP‑to‑MCP proxy), the proxy may extend a still‑valid JWT's effective lifetime if the upstream is mid‑response — deferred decision.

## Consequences

### Positive
- All four 🔴 critical issues from the adversarial review are resolved.
- Audit chokepoint is now genuinely a single point in the FastAPI.
- Boot ordering is acyclic.
- Plaintext credential lifetime is per‑request, not per‑cache‑TTL.
- Audit log is tamper‑evident from Phase 1.

### Costs
- Slight latency increase on the proxy hot path (~2–3 ms p50) from dropping the plaintext cache.
- AdminJS now has a hard dependency on FastAPI being up.
- AdminJS signing key + FastAPI public‑key fetch from Vault Adapter = additional setup steps in the seed job.
- Audit emission is serialized per tenant (acceptable at v1 volume; flagged for higher‑scale follow‑up).
- Vault Adapter is now hit on every proxy request — must be horizontally scalable in Phase 2.

### Risks (net of corrections)
- **App‑layer tenant filter**: a wrapper bug = cross‑tenant leakage. Mitigated by mandatory tenant‑list configuration in the wrapper + arch test + integration test.
- **AdminJS signing key compromise**: short JWT lifetime (60 s) + key rotation + audit on every cross‑service call constrain blast radius.
- **Vault Adapter as bottleneck**: Phase 2 horizontal scaling story is a known follow‑up.

### Threat model
- Hash chain becomes mandatory. App‑layer tenant filter becomes a documented threat with mitigation. AdminJS signing key compromise is a documented threat. Vault Adapter as a hot dependency moves into the operability concerns.

### Iteration 4 contracts

### Phase 2 follow‑ups
