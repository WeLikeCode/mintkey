# ADR-0030: Kubernetes Readiness — restart and replica safety

## Status
Proposed — 2026-07-05

---

## Context

Four defects were identified that prevent Mintkey from surviving a pod restart or running with more than one replica in Kubernetes:

**A1 — Ephemeral broker signing key (`broker/cmd/broker/main.go:45-47`)**
`ed25519.GenerateKey` is called on every process start. Each replica generates a different key; clients that were issued a JWT signed by a dying replica cannot have it verified by the replacement. There is no persistence or cross-replica coordination.

**A2 — In-process OIDC state store (`admin-api/auth/oidc.py:94`)**
`_state_store = {}` is a plain Python dict. State generated by one admin-api pod during the OIDC redirect is invisible to other pods. A round-robin load balancer will cause CSRF state mismatches and broken logins. The dict also leaks memory for abandoned login flows with no TTL.

**A3 — Admin-UI keypair never provisioned; unsigned writes allowed in dev (`signed_request.py:138`)**
The seed-job does not generate `admin_ui_private.pem` / `admin_ui_public.pem`. ADR-0019 requires a signed Ed25519 `AdminUiSignedRequest` JWT on every state-changing call. In practice the guard at `signed_request.py:138` (`if self._public_key is None: # No key configured -> skip (dev mode)`) bypasses signature verification when the file is absent, which is always in a fresh deployment. This silently degrades write security to cookie-only in all environments where the seed-job has not been updated.

**A4 — Literal passwords in a versioned Liquibase changelog (`admin-api/db/changelog/015-app-role-passwords.yaml:9-10`)**
The `ALTER ROLE … PASSWORD` statements embed literal passwords. Any operator who clones the repository has the database role credentials, and rotating them requires editing a file that is nominally immutable (Liquibase locks applied changelogs by checksum).

## Decision

### D1 — Broker signing key: Vault Adapter first, file fallback (addresses A1)

The broker resolves its Ed25519 signing key at startup using the following priority order:

1. **Vault Adapter (`GetCredential` RPC)** — The broker calls the existing `GetCredential` RPC on `vault-adapter:8084` with `svcid_broker` as the service identity. The vault-adapter stores the key material under this well-known service ID using the existing `PutCredential` / `GetCredential` RPCs; no new proto RPC is needed.

2. **`MINTKEY_BROKER_SIGNING_KEY_FILE` file fallback** — If the Vault Adapter call fails or the broker is configured with an explicit path, the broker loads the Ed25519 private key from the file at that path (PEM, mode 0400 minimum). This path is safe for single-replica local compose setups.

3. **Fail closed in production** — When `MINTKEY_ENV=production` and neither source yields a key, startup aborts with a structured log error and a non-zero exit code. The pod enters `CrashLoopBackOff`, which is the correct signal to the operator. In non-production environments a generated ephemeral key is used (preserving the existing dev-only behaviour).

**Key rotation / replica coherence:** The `KeyRing` (already supports multi-key JWKS via `KeyRing.Add(kid, pub)`) retains all public keys for verification until the token max-TTL (10 minutes, ADR-0006) has elapsed. Retiring a key: write the new key to Vault Adapter under a new `kid`, update `MINTKEY_ACTIVE_KID` env, roll pods. Old pods verify with their cached JWKS; new pods sign with the new key. JWKS and REST/MCP wire shapes are unchanged.

### D2 — OIDC state: Postgres table `oidc_login_state` (addresses A2)

OIDC `state` parameters are persisted to a new Postgres table `oidc_login_state` (Liquibase changeset `030-oidc-login-state.yaml`):

| Column | Type | Notes |
|---|---|---|
| `state` | `text` PRIMARY KEY | random opaque token |
| `redirect_uri` | `text` NOT NULL | where to send the user after callback |
| `created_at` | `timestamptz` NOT NULL DEFAULT `now()` | for TTL sweep |

TTL is controlled by `MINTKEY_OIDC_STATE_TTL_SECONDS` (default `600`). A lightweight background sweeper (or `DELETE … WHERE created_at < now() - interval`) purges expired rows. On the callback path the row is **deleted atomically** (`DELETE … RETURNING *`) — single-use semantics. No Redis or additional infrastructure is required; the existing Postgres instance (`mintkey` DB) is reused.

The table does **not** carry `tenant_id` or RLS — login state is pre-authentication and cannot be scoped to a tenant. An explicit exclusion note is added to the RLS architecture test allowlist.

### D3 — Seed-job generates admin-UI keypair; production removes unsigned fallback (addresses A3)

The seed-job (`apps/seed-job/`) gains a step that generates an Ed25519 keypair and writes:

- `admin_ui_private.pem` (mode 0400) — held by the admin-api container via the `bootstrap_secrets` volume.
- `admin_ui_public.pem` (mode 0444) — held by the admin-ui container via the same volume.

Both files are created **if absent** (idempotent). Existing files are not overwritten, making the step safe to re-run on upgrades.

`signed_request.py:138`: when `MINTKEY_ENV=production`, the `if self._public_key is None` branch raises `RuntimeError` instead of skipping verification. Non-production environments retain the skip behaviour for ergonomic local dev without the volume mount.

### D4 — Liquibase changeset 015 uses env-var property substitution (addresses A4)

`admin-api/db/changelog/015-app-role-passwords.yaml` is updated to use Liquibase property substitution (`${db_app_password}` / `${db_subscriber_password}`) referencing the properties `MINTKEY_DB_APP_PASSWORD` and `MINTKEY_DB_SUBSCRIBER_PASSWORD`. These variables are injected at migration time via the Liquibase `liquibase.properties` file or the container's env.

Default values for the property substitution **are not provided** in the changeset — missing env vars cause Liquibase to abort the migration, which is the correct fail-closed behaviour. Existing deployments that already applied changeset `015` are not re-run (the Liquibase `DATABASECHANGELOG` lock is unchanged); the change only affects fresh installs and CI.

## Consequences

### Positive
- Broker signing key survives pod restarts and is consistent across replicas; JWKS/REST/MCP wire shapes are unchanged.
- OIDC login state is durable across admin-api restarts and correct under load-balanced replicas; no new infrastructure (Postgres reuse).
- Admin-UI signed writes are enforced in production from first boot; local dev ergonomics preserved.
- Database role passwords are no longer in git history for new installs; rotation is an env-var change + migration re-run on a fresh DB.

### Costs
- Vault Adapter must be reachable before the broker can start in production (`svcid_broker` path). A retry-with-backoff is required at broker startup.
- `MINTKEY_DB_APP_PASSWORD` and `MINTKEY_DB_SUBSCRIBER_PASSWORD` must be supplied to the migration container; existing compose and Helm values must be updated.
- Upgrading an existing install that already ran changeset `015` with the old literal passwords: operators must manually rotate the Postgres roles after setting the new env vars (no automated migration path — the changeset checksum is unchanged, so Liquibase will not re-run it).

### Wire-shape invariants preserved
- JWKS endpoint response: unchanged (public key content may differ but format is identical).
- `BrokeredTokenClaims` schema: unchanged.
- MCP tool catalog: unchanged.
- `GetCredential` / `PutCredential` gRPC RPCs: unchanged (no proto modification).

---

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Redis for OIDC state | New infrastructure dependency; contradicts ADR-0010 (Postgres LISTEN/NOTIFY over Redis already accepted); Postgres already running. |
| Kubernetes Secret for broker key (not Vault Adapter) | Bypasses the Vault Adapter abstraction; credentials would live outside the encrypted envelope store; inconsistent with ADR-0003. |
| Re-encrypt and re-run changeset 015 | Liquibase checksums the applied changeset; a content change to an already-applied changeset breaks `liquibase validate` on every node that has run it. Property substitution avoids the checksum problem. |
| Mandatory sticky sessions for OIDC callback | Couples login correctness to infrastructure routing; Postgres state is simpler and more robust. |
