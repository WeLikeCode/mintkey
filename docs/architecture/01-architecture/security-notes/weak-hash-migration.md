# Weak-Hash Migration Strategy

**Status**: Accepted-for-prealpha -- accept current SHA-256 fingerprint usage; revisit before v1.0 GA.
**Source session**: `team/remediation/2026-05-18-s5-codeql-weak-hashing/`

## Current state

Three CodeQL `py/weak-sensitive-data-hashing` alert sites were classified in session S5:

- `admin-api/src/admin_api/api/internal.py:119` -- `hashlib.sha256(api_key.encode()).digest()[:8].hex()` for agent api_key fingerprint (DB lookup index, `agents.api_key_fingerprint` column)
- `admin-api/src/admin_api/api/proxy.py:64` -- same pattern for service-key fingerprint (`service_api_keys.key_fingerprint` column)
- `mintkey-models/mintkey_models/audit.py:85` -- SHA-256 on audit chain (`hashlib.sha256(canonical_bytes + prev_hash).digest()`), ADR-0014.7-mandated; NOT a credential hash

## Risk assessment

SHA-256 of a high-entropy 32-byte CSPRNG key is brute-forceable only if the entire 32-byte keyspace is enumerable -- that is 2^256 work, computationally infeasible. CodeQL flags this because the rule pattern matches `hashlib.sha256(<sensitive>)` without context about input entropy. The real risk addressed by the CodeQL rule is rainbow-table attacks against LOW-entropy inputs (e.g., user-set passwords hashed without a salt or key-stretching). That risk does not apply here because:

- Sites 1 and 2: the input is a 32-byte random key generated by `secrets.token_bytes(32)` (CSPRNG output). There is no enumerable dictionary to build a rainbow table from.
- Site 3: SHA-256 is not being used to protect a secret at all. It is computing a tamper-evident hash chain for audit integrity. The security goal is collision resistance, not secret protection.

## Chosen approach (accept-for-prealpha)

**Sites 1 and 2 (api_key fingerprints)**: keep SHA-256. The keys are 32-byte CSPRNG output; brute-force is computationally infeasible. The fingerprint is a lookup index for the DB row that is then authenticated via full Argon2id verification against the stored hash.

**Site 3 (audit chain)**: SHA-256 is ADR-0014.7-mandated. Any change to the algorithm requires:
1. A new ADR superseding ADR-0014.7
2. Migration of all existing `hash`/`prev_hash` columns in the DB
3. Lockstep update of `audit-verify-job/verify.py`
4. Re-verification of all historical audit chains

Changing site 3 without these steps would silently break audit chain continuity for all tenants.

## Revisit trigger

- **Before v1.0 GA**: if the project moves to lower-entropy credentials (e.g., user-set passwords stored as fingerprints), reopen this doc and migrate sites 1 and 2 to HMAC-SHA-256 with a project-static key (`MINTKEY_FINGERPRINT_HMAC_KEY`) plus a maintenance-window key re-issuance or dual-fingerprint cutover (see S5 report for migration plan detail).
- **If ADR-0014.7 changes**: re-evaluate site 3 under the new ADR's algorithm requirements.
- **If agent population exceeds 10,000**: revisit whether the lookup-index approach remains adequate and whether a keyed fingerprint is warranted for defense-in-depth.

## Migration plan for sites 1 and 2 (when trigger fires)

Per `team/remediation/2026-05-18-s5-codeql-weak-hashing/99-report.md`:

1. Add env var `MINTKEY_FINGERPRINT_HMAC_KEY` (32-byte random secret, project-static, loaded from secrets manager).
2. Update `admin-api/src/admin_api/api/agents.py:_generate_agent_api_key()` and `admin-api/src/admin_api/api/api_keys.py:_fingerprint()` to use `hmac.new(HMAC_KEY, plaintext.encode(), hashlib.sha256).digest()[:8].hex()`.
3. Update lookup sites `internal.py:119` and `proxy.py:64` to use the same HMAC computation.
4. Handle existing rows: because the DB stores only the Argon2id hash (not plaintext), existing fingerprints CANNOT be recomputed. Choose one of:
   - **Maintenance-window reissue**: revoke and re-issue all agent/service API keys during a scheduled window.
   - **Dual-fingerprint cutover**: add new `api_key_fingerprint_v2` column; populate on next successful auth; remove v1 column after cutover window closes.
