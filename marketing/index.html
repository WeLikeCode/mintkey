Mintkey
A self-hostable broker that lets autonomous agents discover services, acquire scoped short-lived credentials for them, and call them through a proxy that the real credentials never leave through — with operator-grade observability and per-request audit.

The problem

Autonomous and semi-autonomous AI agents increasingly need to call third-party services to perform real work. To do that, they need credentials.

Today, two unsatisfying patterns dominate. Bake the credential into the agent — embedded API keys in environment variables, prompts, or configuration files. Easy to leak, painful to rotate, impossible to audit at request granularity, and gives the agent the maximum blast radius forever. Or hand-roll a per-integration secret retrieval, pulling credentials from a secrets manager before each call. Better for rotation, but the live credential still lands in the agent's process memory and prompt context — which interacts poorly with prompt injection.

Neither pattern gives an honest answer to the questions that matter: which services can this agent use, what did it actually do with this credential, how do I rotate the underlying credential without touching the agent, how do I revoke an agent's access in seconds, not on next deploy?

Anything less is just a fancier secrets file. (problem-statement.md)

What Mintkey does

Mintkey sits between agents and third-party APIs. Agents speak MCP to discover what services they may use. Mintkey issues a service-bound, scope-bound, time-bound JWT. The agent calls the Egress Proxy with that JWT. The proxy validates the JWT, looks up the real credential, injects it into the outbound request, and forwards it to the backend. The agent never holds a usable credential.

Builder happy path (E2E-01). Agent never touches the underlying credential. — source: E2E-01-builder-happy-path.md

Five properties, each linked to its evidence

Containment of prompt-injection blast radius

A compromised agent can only use the credentials it was granted, only against the services it was granted, only for the TTL of the active JWT, and only via paths the proxy enforces.

S-SEC-1 · ADR-0006
Per-request audit, hash-chained per tenant

Every credential issuance and every proxied request is logged with agent identity, target service, latency, and outcome. The audit log carries a prev_hash chain per tenant.

ADR-0014.7
Rotation without code changes

The operator rotates the underlying credential in the vault; no agent reconfiguration is required. The proxy picks up the new credential on the next request within the cache TTL.

Flow F-OP-03 · ADR-0003
MCP-native service discovery

Agents query list_services, describe_service, and get_openapi over MCP. No out-of-band setup. The agent self-bootstraps a typed client from the served OpenAPI spec.

ADR-0009 · contracts/mcp/tools.yaml
Plaintext credential never visible to the agent

The credential is decrypted only inside the Vault Adapter and used only inside the Egress Proxy's request mutation step. Nothing is cached beyond the encrypted DEK.

S-SEC-1 · ADR-0014.4 · ADR-0017.6

What Mintkey is not

Taken from 02-product-vision.md non-goals:

  • Not a replacement for a general-purpose secrets manager (HashiCorp Vault, Infisical, etc.) for human developers and CI/CD pipelines.
  • Not an agent runtime or orchestrator. Mintkey brokers access; it does not provide the agents.
  • Not an inbound API gateway. The proxy is on the agent's egress path.
  • Not a prompt injection prevention layer. Mintkey contains the impact of a compromised agent; it does not prevent the compromise.
  • Not multi-region active-active. MVP is single-region.
  • Not targeting sub-millisecond proxy latency or 10k RPS per instance. Target is ~100 RPS per proxy instance, scaling horizontally.

How to try it

Five commands against a freshly cloned repo. Full walkthrough: docs/guides/github-quickstart.md. 

git clone <repo-url>
cd mintkey
docker compose up -d
make smoke
open http://localhost:8081   # Admin UI (AdminJS)

make smoke executes E2E-01 end-to-end: bootstrap, operator login, service registration, credential registration, agent creation, permission grant, MCP discovery, token request, proxied call, and audit verification. It completes in 90 seconds or less (S-TEST-1). All 15 long-running containers plus 2 one-shot jobs (Liquibase, seed-job) should report Up (healthy) after docker compose up -d (PORTS.md).

See QUICKSTART.md for prerequisites and step-by-step instructions. See docs/guides/github-quickstart.md for a detailed walkthrough with a live GitHub API as the demo backend.
