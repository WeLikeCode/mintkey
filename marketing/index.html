Self-hosted credential broker for AI agents.

Agents get scoped short-lived access. They never see raw API keys.

Agents call backend services through Mintkey. Mintkey holds the real credential, hands out short-lived brokered tokens scoped to a single service and action, and logs every call to a tamper-evident, hash-linked audit chain. The raw API key never leaves the broker.

Why now

AI agents are calling real APIs. Every major agent framework makes it trivially easy to hand an agent a raw API key — as an environment variable, a system-prompt constant, or a tool argument — and watch it go. What happens when the agent is prompt-injected and tries to exfiltrate that key? What happens when the same key is shared across ten agents and one of them is compromised? Secrets in environment variables do not survive contact with autonomous agents at scale.

Existing secret managers (Vault, Doppler, Infisical, AWS Secrets Manager) are excellent at storing secrets and injecting them into processes. They are not built around the concept of agent identity. They do not know which specific agent called which service at 14:37 UTC, or that the agent's token should have expired 60 seconds ago. When a secret is pulled from a secrets manager into an agent process, the secret is now in the agent's process memory — and may end up in a log, a trace span, or an LLM context window.

Existing API gateways (Kong, Tyk, AWS API Gateway) are built for inbound traffic: rate-limiting, authentication, and routing of requests coming into your service. Mintkey is an egress broker: it sits on the outbound path of agent calls, holds the upstream credential, injects it on the wire per-request, and never hands it to the agent. That is a fundamentally different trust model that existing gateways were not designed for.

Mintkey exists because the combination — agent identity, operator-owned credentials, short-lived brokered access, and per-request audit — is not available as a coherent, self-hostable, open-source component today. It is pre-alpha software. It is not ready for production. But it is ready for platform teams who want to evaluate what this model looks like before building a proprietary version of it themselves.

Who it is for

Platform teams who want their AI agents to call real APIs without leaking secrets. If you are building an agent platform and you want a clear answer to "which agent called which API, when, with what scope, and can I revoke that access in under five seconds" — Mintkey is the component you are likely building yourself today.

Security-conscious operators who want auditable, tamper-evident records of agent activity. Every credential issuance and every proxied request is appended to a hash-chained audit log per tenant. Breaking the chain requires rewriting history — which surfaces immediately on chain verification.

Operators who want to rotate or revoke without touching agents. Rotate the underlying API key in Mintkey; the agents never knew the real key, so they require no reconfiguration. Revoke an agent's permission; the propagation reaches the proxy within five seconds via Postgres LISTEN/NOTIFY — no redeploy, no waiting for JWT expiry.

The problem

Autonomous and semi-autonomous AI agents increasingly need to call third-party services to perform real work. To do that, they need credentials.

Today, two unsatisfying patterns dominate. Bake the credential into the agent — embedded API keys in environment variables, prompts, or configuration files. Easy to leak, painful to rotate, impossible to audit at request granularity, and gives the agent the maximum blast radius forever. Or hand-roll a per-integration secret retrieval, pulling credentials from a secrets manager before each call. Better for rotation, but the live credential still lands in the agent's process memory and prompt context — which interacts poorly with prompt injection.

Neither pattern gives an honest answer to the questions that matter: which services can this agent use, what did it actually do with this credential, how do I rotate the underlying credential without touching the agent, how do I revoke an agent's access in seconds, not on next deploy?

Anything less is just a fancier secrets file. (problem-statement.md)

What Mintkey does

Mintkey sits between agents and third-party APIs. Agents speak MCP to discover what services they may use. Mintkey issues a service-bound, scope-bound, time-bound JWT. The agent calls the Egress Proxy with that JWT. The proxy validates the JWT, looks up the real credential, injects it into the outbound request, and forwards it to the backend. The agent never holds a usable credential.

Builder happy path (E2E-01). Agent never touches the underlying credential. — source: E2E-01-builder-happy-path.md

How Mintkey compares to existing approaches

None of these alternatives are wrong — they are widely used for good reason. Mintkey is not a replacement for a general-purpose secrets manager or an API gateway. It fills the gap that none of them address: an agent never holding a raw credential while still being able to call authenticated APIs, with per-call audit and sub-10-second revocation.

Supported backend auth schemes

These are the auth schemes Mintkey can broker when forwarding agent requests to backend APIs. The scheme is registered once per service by the operator; the agent never configures credentials. Verified against vault.proto and openapi.yaml.

Scheme Status Notes
API key (header) ✓ Shipped e.g. X-API-Key: <secret> injected by proxy. Header name is operator-configurable.
API key (query parameter) ✓ Shipped e.g. ?api_key=<secret> injected by proxy. Query param name is operator-configurable.
Bearer token ✓ Shipped Authorization: Bearer <static-token> injected by proxy.
Basic auth ✓ Shipped Authorization: Basic <b64(user:pass)> injected by proxy.
OAuth 2.0 client_credentials Partial Mintkey stores the client_id/client_secret and caches the resulting access token; token refresh on expiry is in schema and proto but integration coverage is limited. Verify against current OpenAPI before relying on this scheme.
OIDC client secret Partial (operator IdP only) Present in the AuthScheme enum and vault.proto; used internally for the operator identity provider integration. Not a general-purpose agent-to-backend scheme at this stage.
OAuth 2.0 user-delegated Not shipped Tracked in roadmap. Requires user-consent flows not yet designed.
mTLS Not shipped Present in vault.proto enum (AUTH_SCHEME_MTLS = 7) as a placeholder. Not in OpenAPI enum. Tracked in roadmap.
AWS SigV4 / GCP IAM Not shipped Tracked in roadmap. Requires per-provider signing logic in the proxy plugin.

Five properties, each linked to its evidence

Containment of prompt-injection blast radius

A compromised agent can only use the credentials it was granted, only against the services it was granted, only for the TTL of the active JWT, and only via paths the proxy enforces.

S-SEC-1 · ADR-0006
Per-request audit, hash-chained per tenant

Every credential issuance and every proxied request is logged with agent identity, target service, latency, and outcome. The audit log carries a prev_hash chain per tenant.

ADR-0014.7
Rotation without code changes

The operator rotates the underlying credential in the vault; no agent reconfiguration is required. The proxy picks up the new credential on the next request within the cache TTL.

Flow F-OP-03 · ADR-0003
MCP-native service discovery

Agents query list_services, describe_service, and get_openapi over MCP. No out-of-band setup. The agent self-bootstraps a typed client from the served OpenAPI spec.

ADR-0009 · contracts/mcp/tools.yaml
Plaintext credential never visible to the agent

The credential is decrypted only inside the Vault Adapter and used only inside the Egress Proxy's request mutation step. Nothing is cached beyond the encrypted DEK.

S-SEC-1 · ADR-0014.4 · ADR-0017.6

What Mintkey is not

Taken from 02-product-vision.md non-goals:

  • Not a replacement for a general-purpose secrets manager (HashiCorp Vault, Infisical, etc.) for human developers and CI/CD pipelines.
  • Not an agent runtime or orchestrator. Mintkey brokers access; it does not provide the agents.
  • Not an inbound API gateway. The proxy is on the agent's egress path.
  • Not a prompt injection prevention layer. Mintkey contains the impact of a compromised agent; it does not prevent the compromise.
  • Not multi-region active-active. MVP is single-region.
  • Not targeting sub-millisecond proxy latency or 10k RPS per instance. Target is ~100 RPS per proxy instance, scaling horizontally.

How to try it

Five commands against a freshly cloned repo. Full walkthrough: docs/guides/github-quickstart.md. 

git clone https://github.com/WeLikeCode/mintkey.git
cd mintkey
docker compose up -d
make smoke
open http://localhost:8081   # Admin UI (AdminJS)

make smoke executes E2E-01 end-to-end: bootstrap, operator login, service registration, credential registration, agent creation, permission grant, MCP discovery, token request, proxied call, and audit verification. It completes in 90 seconds or less (S-TEST-1). All 15 long-running containers plus 2 one-shot jobs (Liquibase, seed-job) should report Up (healthy) after docker compose up -d (PORTS.md).

See QUICKSTART.md for prerequisites and step-by-step instructions. See docs/guides/github-quickstart.md for a detailed walkthrough with a live GitHub API as the demo backend.
