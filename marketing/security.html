Security posture

What Mintkey claims, what it does not claim, and where to read the evidence. Every claim below has a verification command. Without one, the claim is removed.

Threat model

Mintkey uses a STRIDE-style threat model covering the system as defined in the container view. (source: 05-threat-model.md)

Trust boundaries — source: 05-threat-model.md

Named adversaries

Adversary Position What they can do
Hostile agent (prompt-injected) Untrusted zone Has full control of the agent process: can dump memory, prompt context, environment, request and response bodies to an external endpoint.
Network attacker Untrusted zone Can intercept or replay traffic on the wire between zones. Can attempt to forge agent credentials or JWT tokens.
Curious operator Trusted zone (elevated) Authenticated admin-level access. May attempt to query another tenant's data or escalate their privilege.
Malicious backend External A backend service that echoes the injected credential back in the response body, or impersonates another backend via DNS poisoning.

Read the full threat model: 05-threat-model.md

Credential exposure containment

The practical security difference is what a compromised or prompt-injected agent can leak. In a direct-key setup, the agent can leak the underlying long-lived credential. In the Mintkey path, the agent can leak only the short-lived brokered token it was given. The Egress Proxy remains the place where the real credential is retrieved and injected.

What we claim

Each card below is a claim with: the mechanism that enforces it, the verification command a reader can run, and the source of truth.

Plaintext credentials never appear in any log, audit payload, OTel span attribute, or response visible to the agent.
Mechanism: the credential is decrypted only inside the Vault Adapter and used only inside the Egress Proxy's request mutation step. Span attributes are an explicit allowlist (ADR-0017.6); the proxy holds plaintext only within request scope (ADR-0014.4).
Verification: 
docker compose logs | grep -E "$(cat ./scripts/red-team-fingerprints.txt)"
This grep must return empty. Source: CLAUDE.md "Verification commands" (lines 224–226).
Sources: S-SEC-1 · ADR-0014.4 · ADR-0017.6
Tokens are JWS Ed25519, short-lived, bound to service and scope.
Mechanism: the Credential Broker mints JWTs signed with EdDSA (Ed25519). Claims: {sub: agent_id, aud: service_id, scope: action, jti, iat, exp, tnt}. The proxy-bound JWT TTL is 60 seconds; the standard brokered JWT TTL is 10 minutes. The Egress Proxy fetches the JWKS from the broker; no out-of-band key distribution. (ADR-0006)
Verification: a request_token MCP call returns a JWT that decodes as EdDSA with iss=mintkey/broker. Run: 
python3 -c "
import jwt, json
tok = '<token-from-request_token>'
header = jwt.get_unverified_header(tok)
assert header['alg'] == 'EdDSA', header
print(json.dumps(header, indent=2))
"
Sources: ADR-0006 · ADR-0008
Audit log is hash-chained per tenant.
Mechanism: every audit row carries prev_hash and hash. The genesis row's prev_hash is sha256("mintkey-audit-genesis-v1:" || tenant_id). An append to this chain outside the audit chokepoint would break the chain. (ADR-0014.7)
Verification: 
curl -s -X POST \
  "http://localhost:8080/v1/admin/audit/verify-chain?tenant_id=t_default" \
  -H "Cookie: mintkey_session=<session-cookie>" \
  | jq '.valid'
Must return true.
Sources: ADR-0014.7
All wire IDs are ULIDs with stable prefixes.
Mechanism: every identifier exposed on the wire follows the pattern ^<prefix>_[0-9A-HJKMNP-TV-Z]{26}$. Example: svc_01HX5J9F8V8H8V0CG3F2Y5J6S1. The prefix registry is in ADR-0017.11. IDs that do not match this pattern are rejected by validation in the Admin REST API.
Verification: 
python3 -c "
import yaml, re
spec = yaml.safe_load(open('docs/architecture/contracts/rest/openapi.yaml'))
# Find any schema property named 'id' and check its pattern
# openapi-spec-validator validates the full document
import openapi_spec_validator as v
v.validate(spec)
print('OpenAPI schema valid')
"
Sources: ADR-0017.11
Schema source of truth is Liquibase; SQLAlchemy is a generated mirror.
Mechanism: Liquibase changelogs are the authoritative schema definition. The SQLAlchemy models in mintkey_models/db.py are generated by sqlacodegen and must not diverge. A CI diff asserts this. No column is ever added in SQLAlchemy first. (ADR-0015)
Verification: 
sqlacodegen "postgresql://..." > /tmp/db_generated.py
diff mintkey_models/db.py /tmp/db_generated.py
Diff must be empty. Source: CLAUDE.md lines 214–218.
Sources: ADR-0015
PostgreSQL Row Level Security on every tenant-scoped table.
Mechanism: every domain table has a tenant_id column and a Postgres RLS policy. The application sets app.current_tenant per transaction. An architecture test asserts 100% coverage. (ADR-0008, ADR-0014.8)
Verification: 
pytest tests/architecture/test_rls_coverage.py -v
Must report all tests passed, exit 0. Source: CLAUDE.md lines 230–231.
Sources: ADR-0008 · ADR-0014.8
The Agent API Key is returned plaintext exactly once.
Mechanism: at creation, the API key is returned in the response body and immediately hashed (Argon2id) for storage. The agent.created audit event carries the key fingerprint, never the plaintext. Subsequent reads return only the fingerprint. The broker's resolve endpoint uses constant-time compare even for unknown fingerprints to prevent existence oracles. (ADR-0018)
Verification: 
# Create an agent; record the printed key.
# Immediately GET the agent record.
curl -s "http://localhost:8080/v1/agents/<agent_id>" \
  -H "Cookie: mintkey_session=<session>" | jq '.key'
# Must return null or the fingerprint; never the plaintext.
Sources: ADR-0018 · CLAUDE.md "Audit and security"

What we do not claim

These are genuine gaps. They are not marketing hedges; they are facts about the current state.

  • No formal security audit. Mintkey has not been reviewed by an external security firm. The threat model (05-threat-model.md) is a first-pass STRIDE analysis, not a penetration test.
  • No fuzzing campaign. The integration tests cover known-bad inputs; systematic fuzzing of the wire surface has not been run.
  • No bug bounty. This is pre-alpha; there is no managed offering and no bounty program. Report vulnerabilities via SECURITY.md.
  • The wire surface may change. x-mintkey-stability: experimental means breaking changes can happen at any minor version increment until the surface is promoted.
  • The dev KEK in docker-compose.yml is a fixture, not a production secret. It is a documented dev fixture. Production deployments must supply a real KEK via a separate volume mount with restrictive permissions. (PORTS.md)
  • Multi-region active-active is out of scope. MVP is single-region. (02-product-vision.md non-goals)
  • We do not prevent prompt injection inside the agent. We contain its impact on credentials. A prompt-injected agent can still take any action within its granted permission set until it is revoked. Revocation propagates within ≤5 s (S-OPS-1).
  • The v1 vault backend's KEK co-resides with the ciphertext. If an attacker can read both the credential file and the host filesystem, the v1 backend is defeated. This is documented in ADR-0003. Operators in regulated environments must use v2 (HashiCorp Vault) or v3 (SQL + external KMS).
  • Known open gaps are tracked openly. See open-questions.md. Defense in depth has documented gaps at this stage.

Reporting a vulnerability

Mintkey is a credential broker. A vulnerability in this project is credentials-impacting by definition. Do not file vulnerabilities as public GitHub issues.

Use one of the channels described in SECURITY.md: a private GitHub Security Advisory (GHSA) or email the+security@ciprianiacobescu.com. Include: reproduction steps, affected commit hash (git rev-parse HEAD), impact assessment, and proposed remediation if known.

Full policy: SECURITY.md
