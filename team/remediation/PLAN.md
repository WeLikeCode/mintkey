## Current state (2026‑05‑12)

The stack runs (`docker compose up` → 15 long‑running containers, ~2.1 GiB RSS at idle on a 15.6 GiB host; the 2 one‑shot jobs have exited) — but it is **"skeletons + unit‑tested libraries that the entrypoints don't wire together"**: the E2E‑01 demo can't run past Phase 1; `proxy-plugin` is `unhealthy` (the go‑pdk plugin isn't actually wired); the admin UI doesn't function (no resource adapter; old `@adminjs/sql` half‑imported; a `session` table that doesn't exist); the `seed-job` stops at step 5 of 12 (no AdminJS keypair, no service‑identity boot secrets, no Broker signing key, no Keycloak realm); no Go service emits OTel spans or `/metrics`; `audit.Emit` is a stub that always errors; admin‑api endpoints 500 against the real schema on several paths; `/v1/ready` can never go green; **no container has a memory limit or a restart policy**; `otel-collector` runs `:latest` (unpinned). Two decisions are recorded but not implemented: **ADR‑0018** (classical service API keys for non‑agent clients) and **ADR‑0019** (AdminJS is a backend‑for‑frontend over the admin‑api REST API; write‑auth = `mintkey_session` cookie + `AdminUiSignedRequest` JWT, must agree, identity from the session).

> **Note — ADR‑0019 supersedes part of the old plan.** Where `MEGA_PROMPT.md` Phase 1 said "create the `mintkey_app_ro` read‑only role and set `app.current_tenant` on the AdminJS read connection" — **don't.** ADR‑0019 removes the AdminJS DB connection entirely; admin‑api enforces RLS on every REST call. Drop `@adminjs/sql`, `pg`, and `connect-pg-simple` from `admin-ui`; AdminJS uses a custom `RestResource` adapter over the admin‑api REST API. (PLAN.md's WS‑1/WS‑2/WS‑3 already reflect this; the MEGA_PROMPT phase text is the older framing.)

## Workstreams (do them in dependency order; each leaves the repo strictly better; each has an exit gate that must be green before the next)

### WS‑7a — Container & memory hardening: limits + restart + the obvious tuning *(do this FIRST — it's cheap and it protects the host while everything else churns)*
- Add `deploy.resources.limits.memory` **and** `restart: unless-stopped` to **every** container in `docker-compose.yml`. Recommended limits (observed idle × ~2–3 headroom): `keycloak` 1 GiB · `kong` 768 MiB · `admin-ui` 384 MiB · `admin-api` / `mcp-server` / `mock-backend` 256 MiB each · `broker` / `proxy-plugin` / `kong-syncer` / `vault-adapter` 128 MiB each · `postgres` 512 MiB · `grafana` / `prometheus` / `jaeger` / `otel-collector` 256 MiB each. Total cap ≈ 5.5 GiB — comfortable on a 15.6 GiB host, ~2.5× over idle, and a runaway container now gets OOM‑killed‑and‑restarted instead of crashing the Docker VM.
- Tune the heavy off‑the‑shelf ones: `keycloak` → `JAVA_OPTS_KC_HEAP="-Xms256m -Xmx768m"` (and use the `--optimized` build); `kong` → `KONG_NGINX_WORKER_PROCESSES=2`; `postgres` → explicit `shared_buffers=128MB`, `work_mem=4MB`.
- Pin `otel-collector` to a release tag (drop `:latest`).
- **Exit:** `docker compose up -d` then `docker stats --no-stream` shows every container with a `LIMIT` ≠ host total and a `RESTART POLICY`; deliberately lowering one limit (or `stress-ng --vm` inside a container) triggers an OOM‑kill and an automatic restart. Paste the `docker stats` table.
